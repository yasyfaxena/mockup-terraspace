**Owns:** `payments`, `payment_events`, `refunds` · Conventions: [`README.md`](./README.md)

**Provider:** [PayBridge](https://pt-api.ardial.my.id:55000/docs/integration.md) — a payment orchestration API fronting **Xendit** and **Midtrans** behind one signed REST interface.

This promotes the `payments` module that [`erd-spec.md`](../erd-spec.md) §16.5 deferred.

## 1. How the integration works

```text
 1  POST /bookings                     booking created, status=pending, holds the slot
 2  POST /bookings/:id/payments        we sign + call PayBridge POST /charges
 3      → PayBridge returns            { id, orderId, checkoutUrl }
 4      we persist a `payments` row keyed by orderId
 5  redirect customer → checkoutUrl    PayBridge-hosted page; customer picks a method
 6  PayBridge → POST /webhooks/paybridge
        { event, orderId, amount, currency, provider, timestamp }
 7      verify Ed25519 signature against the platform public key
 8      resolve orderId → payments → booking
 9      payment_succeeded → payment.paid   + booking.confirmed
        payment_failed    → payment.failed + booking stays pending
        payment_expired   → payment.expired + booking.cancelled (releases the slot)
```

### The single most important design fact

**The webhook body carries only `orderId`.** There is no `bookingId`, and `metadata` sent at charge creation is *not* echoed back:

```json
{ "event": "payment_succeeded", "orderId": "TSPC-1-3-18cf2a91b3c",
  "amount": 100000, "currency": "IDR", "provider": "xendit",
  "timestamp": "2026-07-27T09:00:00.000Z" }
```

`orderId` is generated by PayBridge — we never supply it. So the **only** way to connect an incoming payment event back to a booking is a row we persisted at charge-creation time mapping `orderId → bookingId`. Without the `payments` table the webhook is unattributable, and money arrives with no way to know what it paid for.

## 3. Amount conversion — read this before writing code

PayBridge takes `amount` as a **positive integer in the smallest currency unit**. Our `bookings.total_amount` is `NUMERIC(14,2)`. The conversion depends on the currency's exponent:

| Currency | Exponent | `NUMERIC` | → PayBridge `amount` |
|---|---:|---|---|
| **IDR** | **0** | `100000.00` | `100000` |
| USD | 2 | `166.50` | `16650` |
| SGD | 2 | `220.00` | `22000` |

```js
// shared/lib/money.js
export const CURRENCY_EXPONENT = Object.freeze({
  IDR: 0, JPY: 0, USD: 2, SGD: 2, MYR: 2, EUR: 2,
});

/**
 * @param {import("@prisma/client").Prisma.Decimal} amount
 * @param {string} currency
 * @returns {bigint} the amount in the currency's smallest unit
 */
export function toMinor(amount, currency) {
  const exponent = CURRENCY_EXPONENT[currency];
  if (exponent === undefined) {
    throw new InternalError(`No minor-unit exponent for ${currency}`);
  }
  return BigInt(amount.mul(10 ** exponent).toFixed(0));
}
```

> **Get this wrong and you charge 100× too much or too little.** IDR is the dangerous case — it has *no* decimal places, so the instinct to "multiply by 100" overcharges by a factor of 100. Throw on an unknown currency rather than guessing an exponent; `adminSettings.currency` is admin-editable and can be set to anything.
>
> Always validate the webhook's `amount` against `payments.amount_minor` before marking a booking paid (§7).

## 4. Request signing

Every call to PayBridge is signed with our Ed25519 private key. **No new library** — Node's built-in `crypto` supports Ed25519.

**String to sign:**

```text
{timestamp}\n{nonce}\n{METHOD}\n{path}\n{sha256(rawBody)}\n{expiryMs}
```

**Headers:** `x-key-id` · `x-timestamp` · `x-nonce` · `x-request-expiry` · `x-signature` (hex).

### Rules that will bite

| Rule | Consequence |
|---|---|
| `x-timestamp` within **5 min** of PayBridge's clock | Server clock drift causes blanket `401`s — run NTP |
| `x-request-expiry` **capped at 5 min** | Higher values are rejected outright, not clamped |
| `x-nonce` unique per request | Reuse is rejected as replay — use `crypto.randomUUID()` |
| Signature covers the **exact raw body** | Sign the same string you send. Serialize **once**, hash that string, send that string — never `JSON.stringify` twice |
| `path` includes the query string | `/payment-methods/xendit` |

### Configuration

| Env var | Notes |
|---|---|
| `PAYBRIDGE_BASE_URL` | `https://pt-api.ardial.my.id:55000` |
| `PAYBRIDGE_KEY_ID` | → `x-key-id` |
| `PAYBRIDGE_PRIVATE_KEY` | Ed25519 PEM, **base64-encoded** to survive env newlines. Never logged |
| `PAYBRIDGE_APP_CODE` | 4-char app code |
| `PAYBRIDGE_CALLBACK_URL` | Must match the registered URL — its **path** is part of the signed string |
| `PAYBRIDGE_PROVIDER` | Default provider: `xendit` |

All validated in `shared/config/env.js` so a missing key fails at boot.

## 6. `POST /bookings/:id/payments`

Create a checkout session for a booking. **Access:** Customer (owner).

### Request

```json
{ "provider": "xendit" }
```

| Field | Type | Required | Default |
|---|---|:---:|---|
| `provider` | enum | ✖ | `PAYBRIDGE_PROVIDER` |

No amount — it is read from the booking. The client cannot influence what is charged.

### Response `201`

```json
{
  "paymentId": "9c1f…",
  "status": "pending",
  "provider": "xendit",
  "amount": "166.50",
  "amountMinor": 16650,
  "currency": "USD",
  "checkoutUrl": "https://pay.example.com/checkout/session-id#token=…",
  "expiresAt": "2026-09-07T05:12:00.000Z",
  "booking": { "id": "3fa85f64-…", "reference": "TS-8F3K2A", "status": "pending" }
}
```

Redirect the customer to `checkoutUrl`.

### What the service sends to PayBridge

```json
{
  "provider": "xendit",
  "amount": 16650,
  "currency": "USD",
  "customer": { "name": "Ana Putri", "email": "ana@example.com", "mobileNumber": "+628110000000" },
  "description": "TerraSpace booking TS-8F3K2A — Meeting Room A, 15 Sep 2026 09:00–12:00",
  "items": [
    { "name": "Meeting Room A (3h)", "quantity": 1, "price": 15000, "description": "TerraSpace Jakarta" },
    { "name": "Tax (11%)", "quantity": 1, "price": 1650 }
  ],
  "metadata": { "bookingId": "3fa85f64-…", "bookingReference": "TS-8F3K2A" }
}
```

### Errors

| Status | Code | When |
|---|---|---|
| 404 | `NOT_FOUND` | Booking not found, or another user's |
| 409 | `PAYMENT_ALREADY_PAID` | Booking already has a `paid` payment |
| 409 | `PAYMENT_ALREADY_PENDING` | A live checkout session exists — return its `checkoutUrl` instead |
| 409 | `BOOKING_ALREADY_CANCELLED` | Cancelled booking |
| 502 | `PAYMENT_PROVIDER_ERROR` | PayBridge unreachable or `5xx` |
| 504 | `PAYMENT_PROVIDER_TIMEOUT` | No response in time |

### Rules

1. **`customer.name`, `email` and `mobileNumber` are all required by PayBridge.** A user with no `phone` cannot check out — validate before calling and return `422 PAYMENT_CUSTOMER_INCOMPLETE` prompting the profile update, rather than surfacing a raw provider `400`.
2. `items` must sum to `amount`. Tax is a separate line so the total reconciles exactly.
3. **The `payments` row is written before the redirect.** If persistence fails after PayBridge returned a charge, the webhook cannot be attributed — write first, redirect second.
4. `metadata` is stored on PayBridge's side for support lookups. It is **not** returned in webhooks — never depend on it.
5. Strict body validation: any field PayBridge does not recognize returns `400`. In particular, top-level `customerEmail` / `customerName` / `customerMobileNumber` were **removed** from the API — sending them now fails.
6. A pending payment keeps the booking `pending`, which keeps the slot held by the exclusion constraint.

## 7. `POST /webhooks/paybridge`

**Access:** PayBridge only, verified by Ed25519 signature. **Not** session-authenticated.

### Request from PayBridge

```
POST /webhooks/paybridge
x-key-id, x-timestamp, x-nonce, x-request-expiry, x-signature
```

```json
{ "event": "payment_succeeded", "orderId": "TSPC-1-3-18cf2a91b3c",
  "amount": 100000, "currency": "IDR", "provider": "xendit",
  "timestamp": "2026-07-27T09:00:00.000Z" }
```

### Response

`200` with an empty body, **as fast as possible**.

```text
200  accepted (processed, or already processed — both are success)
401  signature invalid
```

### Processing

```text
 1  capture the RAW body (Buffer) — before any JSON parsing
 2  verify x-key-id matches the cached platform keyId; re-fetch if not
 3  rebuild {ts}\n{nonce}\n POST \n /webhooks/paybridge \n sha256(raw) \n {expiry}
 4  verify with the platform public key       → fail: 401, do not process
 5  insert payment_events (nonce UNIQUE)      → conflict: replay, return 200
 6  INSERT … ON CONFLICT (order_id, event)    → conflict: duplicate, return 200
 7  resolve orderId → payments row            → miss: status=ignored, alert, still 200
 8  verify amount and currency match the row  → mismatch: status=failed, alert, do NOT mark paid
 9  transaction: update payments + bookings.payment_status + bookings.status
10  mark event processed; return 200
```

### Event handling

| Event | `payments.status` | `bookings` | Side effect |
|---|---|---|---|
| `payment_succeeded` | `paid`, `paid_at` | `status = confirmed`, `paymentStatus = paid` | Confirmation email |
| `payment_failed` | `failed`, `failed_at` | stays `pending`, `paymentStatus = failed` | Customer may retry (§6) |
| `payment_expired` | `expired`, `expired_at` | **`status = cancelled`** | **Releases the slot** |

### Non-negotiables

| Rule | Why |
|---|---|
| **Raw body, before `express.json()`** | Re-serializing changes whitespace and breaks the SHA-256 hash. Mount `express.raw({ type: "application/json" })` on this route only |
| Verify **before** parsing | Never act on an unverified payload |
| Signed with **PayBridge's platform key** | Not our merchant key pair. Fetch from `/.well-known/paybridge-signing-key.json`, cache, re-fetch when `x-key-id` differs |
| Idempotent | The same `event`/`orderId` may arrive more than once — the unique index makes replay a no-op |
| Return `2xx` fast | Retries are 5s, 30s, 5min, then dead-letter. Do heavy work (email) after responding |
| Unknown `orderId` → `200` + alert | Never `4xx` — that triggers pointless retries for something we cannot fix |
| **Amount mismatch → never mark paid** | The only defence against a charge being altered between creation and callback |

> **This is the second place in the app where middleware order is load-bearing.** Better Auth must mount before `express.json()` ([`libraries.md`](../libraries.md) §2); so must this route, with `express.raw`. Getting either wrong produces failures that look like bad credentials rather than a parsing problem.

## 11. `POST /admin/payments/:id/refund`

**Access:** Admin only. Not staff — this moves money.

### Request

```json
{ "amount": "50.00", "reason": "Customer requested partial refund" }
```

| Field | Type | Required | Notes |
|---|---|:---:|---|
| `amount` | decimal string | ✖ | Defaults to the full unrefunded remainder |
| `reason` | string | ✖ | Max 500 |

### Response `201`

```json
{
  "id": "r1…", "paymentId": "9c1f…", "amount": "50.00", "currency": "USD",
  "status": "succeeded", "reason": "Customer requested partial refund",
  "payment": { "status": "partially_refunded", "refundedAmount": "50.00", "remainingAmount": "116.50" },
  "createdAt": "2026-09-07T06:00:00.000Z"
}
```

### Errors

| Status | Code | When |
|---|---|---|
| 404 | `NOT_FOUND` | No such payment |
| 409 | `PAYMENT_NOT_REFUNDABLE` | Payment is not `paid` — PayBridge rejects with `400` |
| 422 | `REFUND_EXCEEDS_REMAINDER` | Amount above the unrefunded balance |
| 502 | `PAYMENT_PROVIDER_ERROR` | PayBridge error |

### Rules

1. **Refunds are synchronous.** A `201` from PayBridge means the money already moved — there is no pending webhook to wait for.
2. Full refund → `payments.status = 'refunded'`; partial → `'partially_refunded'`.
3. Refunding does **not** cancel the booking. Cancel separately if intended — a refunded booking may still be honoured as a goodwill gesture.
4. `requested_by` records the acting admin. This is the audit trail for money leaving the business.

## 12. Operational concerns

### Abandoned checkouts hold slots

A `pending` booking blocks its time range — correct while the customer is paying, wrong if they close the tab. Two safeguards:

1. PayBridge's `payment_expired` webhook cancels the booking.
2. A `node-cron` sweep cancels bookings that are `pending` with no `paid` payment after **30 minutes**, as a backstop for webhooks that never arrive.

Without the second, one abandoned checkout blocks a room indefinitely.

### Failed webhook replay

Rows in `payment_events` with `status IN ('failed','received')` older than 5 minutes are re-processed by a scheduled job. Since processing is idempotent, replay is always safe.

### Reconciliation

A daily job compares `payments` in `pending`/`awaiting_payment` older than an hour against `GET /charges/:id`, and corrects drift. Webhooks dead-letter after 3 attempts (5s, 30s, 5min) — without polling, an outage on our side during that window loses the event permanently.

### Monitoring

`GET /health` on PayBridge reports `status` plus circuit-breaker state for its Postgres and Redis. Poll it to distinguish a provider outage from our own bug before customers report failed checkouts.

### Never log

`PAYBRIDGE_PRIVATE_KEY`, `x-signature`, and full webhook bodies at info level. Add them to pino's `redact` list alongside the auth headers.
